### S101 — patterns / conventions worth remembering

- **`apiStructuredError(message, payload, status)`** is the canonical pattern when an error response needs structured data the client will render against (quota modals, retry-after, conflict details). Use it instead of raw `json({ success: false, error, ...rest }, { status })`. Lives in `$lib/server/apiResponse.ts`. **The helper spreads payload FIRST then `success`/`error` so a caller passing those keys can't accidentally clobber the contract.**
- **Shared `$lib/server/` helpers when an API route and a load function need the same logic.** `rmHelpers.ts` is the canonical example — `resolveRmDoc` + `getPreferredDsaIds` callable from both `+server.ts` and `+page.server.ts`. Never import across `+server.ts` boundaries — Vite tree-shake semantics make it brittle.
- **Custom-select `position: fixed` pattern is now codebase-wide.** All four select components (`CustomSelect`, `ApplicantSelect`, `BooleanSelect`, `NewSelect`) use the canonical pattern from CLAUDE.md Pitfall #17. The capture-phase scroll/resize listener is what makes it work inside modals — without `useCapture: true` the listener never sees scroll events on nested scrollers.
- **The 3 new pre-flight greps in CLAUDE.md §4** caught one real latent bug (N1 → FORM-3) on first run. Worth running them whenever any form, custom-select, or DC/BT/Top-up code changes — the cost is seconds.

### Architecture rules to honour

- **Cache correctness > speed**: a stale published policy is a data-integrity bug, not a perf bug. The cache MUST invalidate on publish and on cron promotion. If in doubt, don't cache — hit Mongo.
- **Pure adapter**: `pmsToEnginePolicy` is a pure function. Do not let it reach into MongoDB or config files. All inputs come from the `PolicyDocument`.
- **Zod validate the adapter output**: the rule engine crashes silently if it receives a malformed policy. Before returning from the bridge, validate against the same Zod shape the compiler emits. Reuse the compiler's schema if one exists; write one if not.
- **No silent conversions**: if a PMS field has no legacy equivalent (e.g. a new JSON-Logic override that the compiler doesn't understand), throw `UnsupportedPolicyFieldError` and log the policyId. Don't silently drop it.
- **Pino + serverless**: log via `console.error` AS WELL as `logger.error` in the bridge hot path. Pino buffer loss is documented in `hooks.server.ts handleError`.
- **Avoid re-scanning all policies on every eval**: the lookup must be O(1) by `(lenderId, product)`. There's a unique index on `PmsLenderPolicies` — use it. No aggregates, no regex.

### Risks & open questions to resolve early

1. **Schema drift between PMS and compiler** — expect this. Some legacy TS entries have custom fields (`_comment`, hand-crafted JSON-Logic) that don't map 1:1 to the PMS schema. For each drift, decide: (a) extend PMS schema, (b) add a converter shim with a known default, or (c) hard-fail and keep the lender on legacy until migrated. Log your decisions in `legacyCompareRun.migrationNotes`.
2. **Cache invalidation race** — SvelteKit serverless instances don't share memory. Per-instance cache + 60-second TTL is acceptable for v1 (admins don't publish more than ~once a day). If you want stronger consistency, stamp a `policyVersion` int on a lightweight "registry" doc and include it in the cache key.
3. **Affordability calculator + variation matcher** — both currently read from the compiler output. Confirm they also work off `pmsToEnginePolicy` output. If they reach into legacy-only fields, add adapters or stubs.
4. **Performance regression** — the lookup happens inside `evaluateCase()` which runs for every lender on every eval. A 77-lender batch with a 20ms overhead each = 1.5s added. Batch the lookups: pass `lenderId[]` once, resolve all policies in one Mongo round-trip before the per-lender eval loop.

### What happened this session (S88) — production stability saga + error alerting

User reported `/` returning 500 on `rinn.in` in production AND failing to load in dev. Cascade of root causes uncovered, all fixed. **No PMS feature work** — entire session was production hardening.

**Root causes (in order of discovery):**

1. **Dev hang** — Vite 7.3.1 + Node 24 + Windows had a `transport invoke timed out after 60000ms` bug on the SSR module-fetch channel. Fixed by switching to Node 22 LTS + Vite 7.2.7, dropping `server.host: '127.0.0.1'` in favour of `'localhost'`, and removing `watch.usePolling`.

2. **Prod 500 on `/`** — gsap published as CommonJS but `gsap/index.js` uses raw ESM `import` syntax. Vercel's serverless runtime `require()`'s gsap and chokes with `Cannot use import statement outside a module`. Fixed by adding `'gsap'` to `ssr.noExternal` in `vite.config.ts` so Vite inlines + transforms it at build time. Also normalized 3 components that imported `gsap` directly to use the shared `$lib/utils/gsapSetup` wrapper.

3. **Vercel runtime kept defaulting to Node 24** — `engines.node: ">=22.0.0"` was being interpreted by Vercel as "use the highest available major" → Node 24. Fixed by pinning to `"22.x"`. Documented in CLAUDE.md as Pitfall #7 (this is a real footgun for the next major Node release).

4. **Console 403 on every page load** — `+layout.svelte` `registerDevice()` used raw `fetch()`, missing the CSRF header. Fixed by switching to `secureFetch`. Device fingerprints now actually register (was silently failing for weeks).

### Patterns / conventions worth remembering (this run)

  - **Lazy-require native bindings that break vitest.** When a package
    has a `bindings.js` / `.node` native module that fails to load in
    test environments (`mongodb-client-encryption` was the trigger
    here), move the top-level `import` to a typed `import type`, then
    `require()` inside the function body that actually needs it. The
    require only fires at runtime; unit tests never trip it. Pair with
    `vi.mock('the-package', () => ({ ... }))` for tests that transitively
    pull the package in.

  - **Encryption gating pattern: passthrough until enabled + DEKs exist.**
    Don't ship encryption code that throws when the flag is off. The
    csfle helpers passthrough plaintext when `CSFLE_ENABLED !== 'true'`,
    AND only throw when the flag IS true but the CMK is missing or DEKs
    aren't created. This lets the code deploy safely BEFORE the operator
    runs the init script — Phase B routes shipped today without taking
    production down.

  - **Dual-query for plaintext → ciphertext migration.** `findUserByMobile`
    tries the encrypted-mobile lookup first (matches new rows once
    encryption is active), falls back to the legacy plaintext dual-query
    (matches every pre-encryption row). Same pattern for email + PAN.
    Once Phase C backfill completes, the fallback becomes dead code —
    safe to remove or leave.

  - **Type-normalize at the encryption boundary.** CSFLE deterministic
    is BSON-type-sensitive (`encrypt(int 9876543210)` ≠ `encrypt(str '9876543210')`).
    `encryptUserPii` coerces `mobileNumber` to string before encrypting,
    standardizing storage regardless of whether the JWT or onboarding
    flow passed it as number or string.

  - **`encrypt-on-write + decrypt-on-read` discipline at the helper edge.**
    Per-collection helpers (`encryptUserPii`, `decryptUserPii`) walk
    the doc and only touch fields in the registry — non-PII passes
    through unchanged. Callers don't think about which field is which;
    they call encrypt before insert and decrypt after read. Single
    source of truth for the PII surface.

  - **Update by `_id`, not by encrypted-mobile filter.** Once mobile is
    ciphertext in storage, `updateOne({ mobileNumber: plainMobile }, ...)`
    won't match anything. Pattern: find via the dual-query helper to
    get `_id`, then update by `_id`. Applied across signup,
    dsa-onboarding, rm-onboarding, team-member-onboarding, set-role,
    rm/profile, ensureApplicantProfile.

- **Hard-nav fallback for destructive resets.** Clear Form's `goto` was silently canceled by a navigation guard reading stale state, leaving users on a blank page. The defensive pattern: await the goto, check `window.location.pathname`, force `window.location.href = target` if the URL didn't change. Cold reload after a destructive clear is acceptable; stranding users on a blank page is not.

- **Extract when the second consumer needs it.** The browser-reload detection that became Pitfall #42 was inlined across all 6 loan `+page.svelte` files. The semantic bug (`navEntry.type === 'reload'` is frozen at tab load and stale after any SvelteKit client nav) was the SAME in all 6 — but because it was inline, fixing one place didn't fix the others, and the drift went unnoticed for sessions. Rule going forward: when a class-wide check appears in a second route file, extract to a util on the same change.

- **Monotonic-counter pattern for cross-component event signaling.** Pitfall #40's restore-cancel buffer resync uses `cancelledAt` (a monotonic integer counter that ONLY ever increases) plus `cancelledIndex` (the payload). Subscribers cache the last `cancelledAt` they saw and diff against the live value — any difference means a fresh signal. `clearCancelled()` zeros the index but NOT the counter. This pattern beats boolean flags (which need explicit reset and have race windows) and event emitters (which need lifecycle management). Reuse it whenever one component needs to signal another across Svelte's reactive boundary without coupling refs.

### 🟢 Decisions / patterns this session

- **Diagnostic-first over speculative-fix-first** when (source has the fix) AND (tests pass) AND (live repro still fails). Add `clientLogger.warn` at the suspect chain link, ship, wait for next user repro to log the smoking gun. Issue #3 is the textbook case. Replaces "guess again and reship" with "the next failure tells you exactly where."

No new prop, no applicantId plumbing into the selector, no centralized "profile reappearance" pub-sub. Locality wins when the signal is component-scoped.
- **Honest two-variant toast (secured vs unsecured)** rather than one ambiguous "data preserved" string. The two loan families have materially different auto-restore behavior (unsecured pops `_stashedIncomeEntries` immediately on NRI Yes→No, secured needs user tap to trigger S104). Lying about state with a single message would surprise the user; branching on `selectedProfiles.includes(p)` is the honest signal.
- **401 on submit → auto-redirect, not improved inline error**. Form data survives via localStorage; the round-trip is 5 seconds; the inline-error path required a "Log in again" button + corresponding click handler that just navigates to the same `/login?redirect=`. Eliminate the click. (User-confirmed via the morning issue report — the inline string was a dead-end with no recourse.)
- **Stop digging at the network layer when the redirect is the right user-facing fix**. Refresh-token failure root causes (TTL >7d, token-reuse race nuking the session, device-fingerprint mismatch) are all legitimate "needs re-login" cases. Surfacing them as a single redirect is the correct UX regardless of which subroot. If the redirect ever fires when the session is actually fine, that's a different bug — `secureFetch` shouldn't have got a 401 — and we'd dig into refresh round-trip itself.
